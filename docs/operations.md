# Эксплуатация

## Официальный экземпляр

- Бот: [PrivateSEO Аналитика](https://t.me/private_seo_analytics_bot).
- Проверка: `https://analytics-bot-199-189-249-224.sslip.io/health`.
- Код: `/opt/privateseo-metrika-bot`, Python `.venv/bin/python`.
- systemd: `privateseo-metrika-bot`, пользователь `metrikabot`, HTTP на loopback, порт 3008.
- База: `/var/lib/privateseo-metrika-bot/bot.sqlite3`; секреты: `/etc/privateseo-metrika-bot.env` (0600). Содержимое секретов не выводить в логи.
- Периоды и расписание по `REPORT_TIMEZONE` (МСК в официальном экземпляре), независимо от часового пояса ОС. Интерфейс расписания рассчитан на МСК.
- OAuth-приложение с 09.09.2026 разрешает только `metrika:read`, без Вебмастера. Изменение прав у Яндекса отзывает старые токены: до изменения сохранить параметры подключений, затем пройти `/connect` и восстановить счётчик/цели. Расписание при повторном входе сохраняется.

## Проверка и выпуск

1. `ruff check .`, `ruff format --check .`, `pytest -q` в venv. Тесты не требуют настоящих токенов.
2. Сохранить согласованный снимок через `sqlite3.Connection.backup` / `python -m metrika_bot.backup`, старый код, unit и env. Хранить копии закрытыми; базу — в каталоге штатной ротации 14 дней. Отдельно проверить сохранность ключа Fernet: база без ключа не восстанавливает доступы.
3. Проверить миграцию на **копии**: значения токенов, счётчиков, целей и расписания сохранены, `PRAGMA integrity_check = ok`, `foreign_key_check` пуст. `_init` выполняет только добавочные миграции; ссылки OAuth прежней версии потребуется создать заново.
4. Остановить service, выложить исходники (исключая `.git`, `.venv`, `.env`, базы и кэши), сохранить владельца `metrikabot`. При изменении зависимостей обновить venv. Установить unit из `deploy/`, выполнить `daemon-reload`, запустить service.
5. Проверить `systemctl is-active`, свежие сообщения `journalctl`, публичный `/health`. Проверить отчёт и кнопки на аккаунте владельца. **Не запускать второй polling-процесс.** `set_profile_texts()` вызывается отдельно при правке описания; меню команд обновляется при старте.
6. Обновить документацию, коммит и push; дождаться зелёного GitHub Actions.

Откат: остановить service, вернуть архив кода и прежний unit, при необходимости согласованный снимок БД; после восстановления убрать относящиеся к заменённой базе `-wal`/`-shm`, вернуть владельца и права. Запустить и проверить `/health`. Секреты восстанавливаются отдельно; не менять ключ без повторного шифрования токенов.

## Работоспособность и нагрузка

`/health` возвращает 503, если polling или планировщик не отчитывались более 180 секунд, и 200 при работе обоих. Главный процесс обнаруживает завершившийся polling/scheduler/HTTP-поток; systemd перезапускает процесс. Ошибка чтения БД в одном цикле планировщика не завершает поток: следующий цикл через минуту.

Управление и отчёты выполняются в разных очередях. Не больше одного отчёта на чат, две сборки одновременно, максимум 32 активных/ожидающих отчёта. Переполнение получает понятный ответ; повторные нажатия не увеличивают очередь. Управление — четыре работника и 64 места. Удаление и отключение обрабатываются через отдельный путь и сериализуются с последней проверкой перед отправкой. Telegram-доставка, уже начатая до удаления, может завершиться; после подтверждённого удаления новые отчёты не отправляются.

Запросы Метрики: максимум два одновременно, до 15 запросов/сек и до 180 запросов отчётов за 5 минут на токен. Серверный 429 дополнительно останавливает повтор на указанный срок; 5xx имеет ограниченный повтор. Локальный бюджет запуска запросов одного отчёта — 180 секунд, таймаут одного HTTP-запроса — 30 секунд. При отзыве доступа автоматические отчёты приостановлены до `/connect`; временные ошибки повторяются не раньше чем через 5 минут. Уведомление о временной ошибке — один раз за день до успешного отчёта.

Один login Яндекса может иметь несколько токенов: локальный лимит не объединяет их; окончательный лимит контролирует Яндекс, ответ 429 обрабатывается. Лимиты не являются обещанием пропускной способности для массовой рассылки. HTTP принимает максимум 16 одновременных обработчиков.

## Резервные копии и приватность

`privateseo-metrika-backup.timer` запускает ежедневный согласованный backup в `/var/backups/privateseo-metrika-bot`, файлы `bot-*.sqlite3`, ротация 14 дней. Шифруются OAuth-токены внутри базы, **не весь файл базы**. Хранить резервную копию env отдельно с правами 0600. Временные копии для проверок и реальные отчёты удалить после проверки; предрелизную базу перенести в каталог ротации.

Тексты отчётов и сырые выгрузки не сохраняются. Сохраняются параметры кнопки отчёта (счётчик, цели, период) до 30 дней и технические события до 90 дней. `/delete_me` и блокировка удаляют пользователя, связи, параметры отчётов и его события; `/disconnect` отменяет также ожидающий OAuth. При восстановлении старого снимка нельзя автоматически запускать рассылку до сверки удалений и настроек после даты снимка.

OAuth callback не должен попадать в access-log с query string: там код и state. Штатный обработчик пишет только path; reverse proxy также должен исключать query из логов. Для воспроизведения сбоев не публиковать callback URL, заголовки Authorization и содержимое env.

## Компактная сводка — 23.09.2026

Первый отчёт отправляется обычным HTML-сообщением Telegram: три показателя, все активные источники (по числу визитов сейчас), точные даты сравнения и один ряд кнопок «Подробнее / Настройки». Заголовки Rich Message и повторяющиеся рекомендации убраны из сводки. Полный отчёт сохраняет таблицы Rich Message с обычным HTML как резервным форматом. Старые кнопки отчётов и настройки продолжают работать; сравнение периодов и сбор данных не менялись. Предупреждения о выборочных данных, недоступных целях и задержке Метрики сохраняются. Предупреждение о неполной выгрузке страниц показывается в деталях рядом со страницами.


## Календарные отчёты, источники и график — 23.09.2026

`dashboard.py` задаёт календарные окна и понятные даты: день = вчера/позавчера; неделя и месяц = текущий период по вчера к равной прошедшей части прошлого. В понедельник/первое число — предыдущий полный период. Разная длина месяцев сравнивается по среднему за день с явной подписью; подробности тоже используют эту логику. Автоматическое расписание остаётся дневным/недельным, `/month` и кнопка месяца доступны вручную. При нажатии периода используется дата исходного сообщения, а не сегодняшняя дата спустя время.

Добавочные колонки `connections`: `visible_sources` (NULL = все, [] = ни одного), `chart_enabled` (1), `report_view` (week). Выбор сохраняется и проверяется по поколению подключения. Контексты новых отчётов сохраняют период, цели, источники и вид графика; старые контексты без `view` продолжают сравнивать прежние окна. Общие итоги и цели — весь сайт; источники скрываются только из списка, графика и советов про источники. Страницы в деталях — все источники, это подписано.

История: `/stat/v1/data`, группировки `ym:s:date,ym:s:trafficSource`, для целевых визитов отдельный OR-фильтр выбранных целей. До 5000 строк с пагинацией; неполная выгрузка отключает график, не превращает пропуски в нули. NULL рвёт линию. Единые фильтры роботов, timezone, квоты и срок сборки сохраняются. История начинается не позже начала прошлого сравниваемого периода, минимум 14 дней. Сырые данные и PNG живут только в памяти.

График — Pillow, PNG, Telegram `sendPhoto`; период переключается через `editMessageMedia` в том же сообщении. Два отдельных масштаба для источников и целей. При >5 источниках на графике четыре крупнейших и сумма остальных выбранных, в тексте — каждый отдельно. Подпись ограничена 1024 UTF-16 единицами: сначала сокращается число отдельных целей до 0, полный список всегда в деталях. Если подпись всё ещё длиннее или график недоступен, отправляется текст. При сбое переключения старый график не получает новую подпись с чужим периодом. Нужны `Pillow>=12.1.1,<13` и шрифт `fonts-dejavu-core` (Docker уже включает), либо `CHART_FONT`.

Перед выпуском: согласованный backup базы/ключа, миграция на копии с сохранением прежних полей и integrity/foreign keys; полный pytest и Ruff; живой график владельцу и смена периода на том же message_id. Второй polling запрещён.


Приёмка v0.3.0: 104 теста; миграция копии сохранила все прежние значения, целостность и расшифровку доступа. На настоящей Метрике построены 53 точки истории для двух источников и целей, владелец получил PNG; три режима проверены через обработчик кнопок с настоящим редактированием одного Telegram message_id. Картинки и копия для проверки удалены после приёмки; штатный backup остаётся в 14-дневной ротации. Обнаруженная при выкладке недоступность Pillow служебному пользователю исправлена: установку зависимостей делать с `umask 022`, до рестарта проверять импорт и загрузку шрифта через `runuser -u metrikabot`. Секреты и резервные копии сохраняют закрытые права. Pillow импортируется только при построении графика; его ошибка не останавливает бот.


## График по запросу — 23.09.2026

Существующее `chart_enabled` задаёт режим: 1 = «График сразу», 0 = «График по кнопке», без миграции схемы. В текстовом режиме история не загружается и Pillow не вызывается; сводка сохраняет показатели, источники и цели. Кнопка `chart:<context>` собирает график отдельным сообщением с исходными датой, целями и источниками, не меняя настройку. Переключение периода на фото сохраняет фото, на тексте — текст. Проверки поколения подключения и очередь отчётов общие; старые настройки `src:…:chart` совместимы. Откат пользовательского режима — «Что показывать → График сразу»; откат кода — архив перед выкладкой, схема БД прежняя.
